# Plan: keep Home Assistant responsive as installs grow (#1726, #1727, #1730)

## Outcome
No Climate Advisor job blocks Home Assistant's event loop for more than about 50 ms on a Raspberry Pi 4, at any zone or
sensor count, and nothing changes what the occupant sees or what the model learns except where stated (#1726).
When a machine cannot keep up, Climate Advisor degrades the outlook first, never the next 48 h, and says so.

Pi figures in this plan are x86 measurements × 4–6 (#1722: 99 s Pi vs 21–24 s x86). No Pi reading is planned
(owner decision 2026-11-27); phase 4's self-measurement is the calibration.

## Owner decisions (2026-11-27: "plan based on your recommendations")
1. #1726: option (c′): skip the cold restart when the warm LM converged and improved its own start cost by < 2%.
2. #1727: the build moves to an executor thread; the plan lands one await later and readers outside the cycle may see
   the previous plan for up to one build.
3. Under load the outlook (48 h–week) refreshes every k-th cycle; it is not dropped. Floor: never degrade 0–48 h;
   the last tier caps the horizon at 60 h.
4. Capacity: costs and the current tier on the Debug card, plus one WARNING log on sustained overload. No new entity
   and no Repairs notice now (both are hard to undo); revisit with field data.
5. #1730 scope includes the Status chart finding and every large store through one shared writer/reader (v4/v3
   archive, cycle store, forecast archive, chart log, learning state, worker pipe).
6. Cycle-store caps stay (3,000 × 400). The registry costs at the caps. Startup loads are held to the same
   "no single long hold" rule (the shared helper makes that cheap).
7. Not needed: no request to the #1722 reporter.

## Simplification review (2026-11-27, owner asked for the simplest path)
Research: HA core source (2026.2.3), HACS, Predbat, EMHASS; orjson measured on our file shapes. Changes to the
first draft of this plan:
- **orjson, one element per line, replaces the custom chunked-JSON helper.** HA pins orjson (3.11.5). orjson does
  not release the GIL, and a whole-file call is still 230–370 ms on a Pi, but per-element calls hold it about
  0.02 ms each (max loop gap 7–9 ms measured). The file stays plain JSON that `json.loads`, and so every older
  version, reads. About 30 lines, shared.
- **The timeline build stays synchronous; only the outlook leaves the loop.** The latch keeps only steps before the
  48 h promise end, and the signature trims to it, so the 0–60 h plan is built on the loop as today (about 11 ms x86
  after phase 1) and the display-only outlook (60 h–week) is built in the executor, rate-limited, skipped if one is
  running, and spliced past the seam. No single-flight or latest-wins machinery; every caller that reads the plan
  right after building it stays as it is.
- **The tier controller is replaced by measurement plus one rule.** HA has no public loop-lag API (its detectors see
  blocking I/O only, or need asyncio debug mode), so we measure: our own job times and a cheap loop-lag probe. Rule:
  when lagging, rebuild the outlook less often. Logged once per state change.
- **Rejected:** HA `Store` (writes on the loop by default, 2.5× larger indented files, still one whole-file load,
  file migration); `asyncio.sleep(0)` yielding (turns the pure planner async, same ripple as a thread); whole-file
  orjson alone (still over budget on a Pi).

## Phases (one PR each; every PR bumps the version, CHANGELOG, fix_history)
### Phase 1: exact speedups, no behaviour change (#1727 L0, #1730 core)
**Phase 1 merged (PR #1733, v0.9.88).**
- `operation_timeline._Simulator`: precompute per-step inputs once per build (`_grid`, `_interp(keys)`), reuse the
  no-window base run's prefix up to each candidate's first span. Byte-identical `DetailedTimeline`.
- `v4_archive._Line.series(start, end)` by index; `past_span` from the line's first/last valid index. Used by
  `build_chart_v4`, the accuracy page, and the payload builders; chart rows by `ChartStateLog._time_sorted_rows`
  bisect (#1598), anchored on the request's `before`.
- One shared store writer/reader: orjson per element, one element per line (`b",\n".join(...)`); read by
  splitting lines, falling back to `json.loads` for an older layout or for NaN/Infinity (orjson rejects them).
  Adopted by every store in decision 5 and by `process_offload._encode/_decode`. Check per store before switching:
  orjson writes NaN as `null` and non-ASCII as UTF-8, so every reader, including the oldest supported release, must
  accept `null` where a NaN could be stored; a store where it cannot keeps stdlib for those values. Guards: a
  round-trip test per store (new writer → old reader gives the same in-memory state), and a max-hold check.
- V4/V3 archive: columnar load (no per-value `put_if_absent`), same file format. The column serializer is deferred:
  after orjson the save is under budget and its Python part yields every few ms.
- Payload builders: compact forecast snapshots, decoded in the worker (`ForecastArchive._decode` becomes a hass-free
  module function; add it to the import-closure guard).
- `_v4_display_pending`: bisect the 30-day slice (reuse #1598).
- Registry (#1728): re-measure and reclassify (`V4Archive.load` leaves `over_budget`; `CycleStore.load` gets
  `cpu_ms`; stale `get_chart_data`, `_build`, `_v4_archive.save` numbers refreshed).
- Guards: byte-identity tests per store and for the timeline (week fixtures, 5 day types × v3/v4); replace the
  250 ms week-build wall-time test with a deterministic work count (sim steps per build) on a hot v4 168 h fixture.

**Status (2026-11-27):** code committed as 276a8a6b; docs updated by the Scribe (claude.md Thread-Safety second form and registry, DEVELOPMENT, process-offload brief, v4-shadow, forecast-archive, chart-log, state-persistence, operation-timeline, architecture map, sim-harness). ### Phase 3: #1727, the outlook leaves the loop — DROPPED (owner decision 2026-11-27)
Built and verified on a local branch, not merged. Verification found that a 60 h loop cap changes which window
periods are accepted inside 0–48 h for v4 houses (about 0.5% of builds, both directions; 0 in 6,000 v3 builds):
v4's house mass carries a window's effect for days, so today's acceptance depends on the forecast's days 5–7.
That breaks the "0–48 h must not change" floor, and exact parity needs the full build, so the owner dropped the
phase. Phase 1 already cut the hot 8-day v4 build from 209 to 45 ms (x86); phase 4 measures what is left.
Original design, kept for reference:
- The loop-side build caps the horizon at now + 60 h (`TimelineLatch.update(..., end_cap=...)` or in
  `_timeline_snapshot`). Callers stay synchronous.
- The full-horizon build runs in the executor every N cycles or on a forecast change, at most one at a time per
  zone; its steps and path past the seam are spliced into what the surfaces show. A stale outlook is harmless: it is
  never latched.
- The seam: a window period crossing 60 h must not produce a spurious `windows_close.horizon` step or a path jump;
  place the seam at a quiet point after 54 h, or drop `horizon`-tagged steps near it. Decide the source of
  `hvac_minutes` and the summary. Confirm `snap.house_stepper` is stateless before a thread reads it.
- Capture `path_fn`'s live reads (`_hourly_forecast_temps`, `_zone_service_of`) for the executor build, which also
  takes `_build_predicted_indoor_future` off the loop for the outlook (#376).
- Registry: one `short_cpu` entry. Guards: 0–48 h plan identical with and without the cap (week fixtures); the
  seam produces no extra steps.

### Phase 4: the safety net (owner's strategy)
- Self-measure: `_timeline_last` keeps last/max/EWMA of build thread CPU; `_executor_job` records thread CPU per job
  (reuse `perf_probe.callable_name`); shown on the Debug card.
- A loop-lag probe: `hass.loop.call_at` every 0.5–1 s, recording lateness; rolling max and p99 on the Debug card.
- No adaptive rule (phase 3 dropped, so there is no display-only outlook to throttle; anything else would change
  the plan). Instead: an "overloaded" state when the probe or our own jobs are over budget for a sustained period
  (back to normal after a long calm period), shown on the Debug card, with one WARNING log on entering and leaving
  it and one more if it persists for 24 h. Field data decides whether a degrade rule is ever needed.
- A global cap on concurrent worker processes (cores − 1).
- Perf probe: subtract nested executor spans from loop rows, time FakeScheduler sync callbacks, add a generated
  household with a 6–7 day forecast and a v4 model to the nightly perf report.

**As built (v0.9.89, `self_measure.py`):**
- Per-job thread CPU: `coordinator._executor_job` wraps each callable with `SelfMeasure.timed` (`time.thread_time`
  inside the worker thread, keyed by `callable_name`; last/max/count/EWMA; at most 64 names, then `<other>`). The
  timeline build reports through `record_loop_cost`. Shown on the Debug card group "performance".
- Loop-lag probe: one raw `hass.loop.call_at` callback per Home Assistant instance every 1 s (zones share it by a
  reference count), lateness against `loop.time()`, a fixed ten-minute ring (p99 and max on the card); a stall is one
  big sample. Boundary note: `docs/HA-BOUNDARY-EXCEPTIONS.md` §5.
- Overloaded state, **a minute is judged on loop lag only** (the real harm): over budget when at least 3 of that
  minute's own ticks were later than 50 ms. Our own costs are recorded and shown but never flag a minute: on a Pi
  routine work (hourly v4 archive save about 1.75 s, cycle store save about 2 s, an 8-day v4 timeline build about
  225 ms) would otherwise keep a 3-4 zone install "overloaded" permanently. Enter at 10 of the last 60 minutes;
  leave after an hour without one. One WARNING on entering, naming our biggest recent cost as the likely cause only
  when costs of ours of at least 50 ms turned up in at least half of the late minutes (else "the delay is probably
  elsewhere in Home Assistant"), one INFO on leaving (counted from the first late minute), one more WARNING at 24 h.
  Owner decision 4: Debug card and WARNING only, no entity, no Repairs notice.
- Worker cap: `process_offload.worker_limit()` = cores - 1 (`os.process_cpu_count()` on 3.13+), at least 1, one
  semaphore per event loop; the job timeout counts from slot acquisition.
- Perf probe: nested executor spans subtracted from loop/task/callback rows, `callback` kind for scheduler timer
  callbacks, `run_heavy_household` rows in the nightly report.
- Tests: `test_self_measure_1730.py`, `test_self_measure_wiring_1730.py`, `test_worker_cap_1730.py`,
  `test_perf_probe_1730.py`, `tests_ha/test_self_measure_realha_1730.py`.

## One-way vs two-way
- **One-way (ask the owner):** merging each PR; any stored-format change (none planned); a new entity or Repairs
  notice (not planned); any golden scenario edit; deploying (never).
- **Owner-approved behaviour changes:** #1726 learned parameters (~1% shifts, replaced nightly); phase 4's worker
  cap (jobs queue on boards with 2 cores or fewer); #1734 window periods judged over max(now+72 h, close+24 h).
  (Phase 3's plan timing and phase 4's degraded tiers were dropped.)
- **Two-way:** everything else.
